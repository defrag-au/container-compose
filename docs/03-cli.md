# 03 — The CLI

Status: design, 2026-10-24.

Ten commands. Nothing else: no plugin loading, no shell completion generated by
default, no aliases beyond the ones written here.

```
container-compose [global flags] <command> [command flags] [args]
```

## Global flags

| flag | default | meaning |
|---|---|---|
| `-f, --file <path>` | `./stack.toml` | The stack file. No upward search: `cd` must not change which stack is meant. |
| `-p, --project-name <name>` | the file's `name`, or the directory name | Overrides the project name. Useful for a second copy of the same stack. |
| `--runtime <path>` | `container` | The `container` binary to invoke. Exists for the fake runtime in [`05-testing.md`](05-testing.md), and for a preview build. |
| `-v, --verbose` | off | Echo every `container` argv before running it. |
| `--no-color` | off | Disable ANSI colour. Also honoured from `NO_COLOR`. |
| `--no-env-check` | off | Skip the git check on the env file. |

`--json` is per-command rather than global, because on some commands it changes
the output document rather than the formatting.

Global flags may appear before or after the command. `--` ends flag parsing.

## `plan`

The dry run. Reads the stack, queries the runtime, and prints what `up` would
do. Makes no changes.

```sh
container-compose plan
container-compose plan --commands
container-compose plan --json
```

```
PLAN  mitos  config 3f9c1a2b7d4e0055  (stack.toml)

  keep      network    default          subnet 192.168.64.0/24
  create    volume     mitos-spool      size 200G, journal ordered
  create    volume     mitos-cache      size 20G
  create    volume     mitos-ledger     size 100G
  create    container  mitos-sieve      ghcr.io/defrag/wallet-sieve:0.4.0
  create    container  mitos-ledger     ghcr.io/defrag/token-ledger:0.4.0
  start     container  mitos-sieve
  wait      container  mitos-sieve      healthy, up to 120s
  start     container  mitos-ledger

9 steps. Run `container-compose up` to apply.
```

Actions are `keep`, `create`, `recreate`, `start`, `stop`, `delete`, `wait`,
`pull`, `build`, `warn`. The last is for a condition that does not stop `up` —
an orphan container, or the isolated-network DNS caveat.

`--commands` replaces the table with the exact argv, one block per step:

```
# create container mitos-sieve
container create \
    --name mitos-sieve \
    --label dev.container-compose.project=mitos \
    --label dev.container-compose.service=sieve \
    --label dev.container-compose.config=3f9c1a2b7d4e0055 \
    --label dev.container-compose.schema=1 \
    --network default,alias=sieve \
    --env RUST_LOG \
    --volume mitos-spool:/spool \
    --volume mitos-cache:/cache \
    --volume /Users/damo/code/defrag/mitos/fixtures:/fixtures:ro \
    --publish 127.0.0.1:8184:8184 \
    --cpus 4 \
    --memory 6G \
    --ulimit nofile=65536:65536 \
    --init \
    ghcr.io/defrag/wallet-sieve:0.4.0 \
    wallet-sieve serve --db /cache/sieve.db --immutable /chain/db/immutable
```

This is the trust feature: the argv shown is the argv executed, character for
character. A golden test asserts that `plan --commands` and the fake runtime's
recorded argv agree — see [`05-testing.md`](05-testing.md).

`plan --json` emits one document with the same steps plus `argv` per step. It is
the machine-readable form of the two above, not a third source of truth. In the
implementation `detail` is a tagged union (one variant per resource kind), not a
free-form map; the JSON below is abbreviated, not untyped:

```json
{
  "project": "mitos",
  "config": "3f9c1a2b7d4e0055",
  "file": "/Users/damo/code/defrag/mitos/deploy/local/stack.toml",
  "steps": [
    { "action": "keep", "resource": "network", "name": "default",
      "detail": { "subnet": "192.168.64.0/24" }, "argv": null },
    { "action": "create", "resource": "container", "name": "mitos-sieve",
      "detail": { "image": "ghcr.io/defrag/wallet-sieve:0.4.0" },
      "argv": ["create", "--name", "mitos-sieve", "..."] }
  ]
}
```

`plan` exits 0 when the plan is executable, 3 when it contains an action that
would be refused (an unowned name, a volume that must be recreated), and 2 when
the file does not validate. It never exits 4 — nothing has run.

Every refusal is decided in the plan phase, before the first pull, so exit 3
always means nothing was executed. A name that is taken between the plan and the
create is a runtime failure (exit 1), not a refusal.

`plan` and `up` also refuse (exit 3) when the env file is tracked by git or not
ignored; `config` warns instead. `--no-env-check` skips the check.

## `up`

```sh
container-compose up [SERVICE...] [-d] [--wait] [--timeout 15s]
container-compose up --no-recreate --keep-started
container-compose up --dry-run
```

| flag | default | meaning |
|---|---|---|
| `-d, --detach` | off | Create and start, then exit. Refused if any service has `restart` other than `no`. |
| `--wait` | off | With `-d`, wait for readiness before exiting. Without `-d`, readiness is waited for anyway. |
| `--timeout <duration>` | `15s` | Passed to `container stop --time` on stop paths. |
| `--no-recreate` | off | A config-hash mismatch is an error (exit 3) instead of a recreate. |
| `--keep-started` | off | On failure, leave services started by this invocation running. |
| `--no-stop-on-exit` | off | On Ctrl-C, leave everything running (the `-d` behaviour). |
| `--dry-run` | off | Alias for `plan`. |

With a service list, `up` starts those services **and their dependencies**;
everything else is planned but not started. A service named in the list that
does not exist is a usage error (exit 2).

Foreground `up` supervises: it reconciles, waits for readiness, then polls the
runtime until Ctrl-C. A project has one supervisor at a time; a second `up`
refuses (exit 3, naming the pid).

Progress goes to stderr, one line per step, so stdout stays clean for `--json`:

```
✓ network default                     kept
✓ volume mitos-spool                  created (200G, ordered)
✓ container mitos-sieve               created
→ container mitos-sieve               starting
… container mitos-sieve               waiting for health (0/4)
✓ container mitos-sieve               healthy after 12.4s
```

The final line is either `stack mitos is up (2 services)` or an error naming the
step that failed.

## `down`

```sh
container-compose down
container-compose down --volumes
container-compose down --dry-run
```

| flag | default | meaning |
|---|---|---|
| `--volumes` | off | Delete this project's volumes after the containers are gone. Prints each before deleting. |
| `--timeout <duration>` | `15s` | Graceful stop window per container. |
| `--dry-run` | off | Print the teardown plan without running it. |

`down` is idempotent: a project with nothing running exits 0 and says so. It
stops and deletes only resources carrying the project label. It never uses
`--all`, `prune`, or `network delete --all`.

While a supervisor holds the project lock, `down` refuses (exit 3, naming the
pid): stopping containers the supervisor would immediately restart is not a
teardown. Stop the supervisor first.

`down` exits 0 even when some resource was already absent; a runtime error
(permission, apiserver down) is exit 1.

## `ps`

```sh
container-compose ps [--json] [--probe]
```

```
NAME           SERVICE   STATE    HEALTH    IMAGE                                   PORTS
mitos-sieve    sieve     running  healthy   ghcr.io/defrag/wallet-sieve:0.4.0       127.0.0.1:8184->8184
mitos-ledger   ledger    running  unknown   ghcr.io/defrag/token-ledger:0.4.0
```

`HEALTH` is `healthy`, `unhealthy`, `starting`, `unknown`, or `—` (not running).
It is not derived from the runtime, which records none: a running supervisor
publishes the last result per service to
`~/Library/Caches/container-compose/<project>.json`, and `ps` reads it. No file,
a dead pid or a config-hash mismatch prints `unknown`, with one footnote naming
the last observation, if any. `ps` never runs a probe itself unless `--probe` is
given, which runs each healthcheck now and reports `source: "probe"`. It shows
containers belonging to the project even when the stack file is absent, which is
what makes an interrupted session recoverable; health then comes from the cache,
or is `unknown`.

A kept one-off `run` container is shown only while it is running; `down` ignores
it.

`ps --json` emits an array of typed records; `health` is an object with `state`,
`checked_at` and `source` (`supervisor`, `probe`, or `none`), not a formatted
string.

## `logs`

```sh
container-compose logs [--follow] [-n 200] [SERVICE...]
```

Following is `--follow` only: `-f` is the global `--file`, and clap refuses two
meanings for one short flag.

`logs` is `container logs` per service. With more than one service, every line
is prefixed with the service name; with one, it is passed through unmodified.
`-n` is passed through and is the runtime's line count, not ours. Whether a
stopped container's stored output comes back is one of the runtime facts to
confirm ([`04-runtime.md`](04-runtime.md#facts-to-confirm-in-the-build-session),
question 3).

## `exec`

```sh
container-compose exec api -- sh -lc 'ls -la /data'
container-compose exec -T api -- cat /etc/os-release
```

`exec` allocates a TTY by default when stdin is a TTY and `-i`/`-t` are not
given; `-T` disables both. Everything after `--` is passed verbatim. The service
must be running — `exec` does not start it.

## `run`

```sh
container-compose run api -- python -c 'print(1)'
container-compose run --keep api -- sh
```

A one-off container with the service's configuration, named
`<project>-<service>-run`, attached to the terminal, with the project's network
and bind mounts. It is not supervised and is removed on exit unless `--keep` is
given. `-T` disables the TTY as in `exec`. It is not part of the stack: `ps`
shows it only while it lives, `down` does not know about it, and a second
concurrent `run` of the same service is refused rather than silently named twice.

A service that mounts a **named volume** cannot be `run` while its own container
is running: the runtime allows only one running holder of a named volume, so
`run` refuses with exit 3 and points at `exec` instead. Bring the service down,
or use `exec` for a shell in the running container.

## `build` and `pull`

```sh
container-compose build [SERVICE...] [--no-cache]
container-compose pull [SERVICE...]
```

`build` runs `container build -t <project>-<service>:local -f <containerfile>
<context>` for each service with a `[services.<name>.build]` table, in
dependency order. `--no-cache` is passed through. Services without a build
table are skipped, not an error.

`pull` runs `container image pull` for each service with `pull != "never"`.
A `pull = "never"` service is skipped and reported as such, and a service with a
`build` table is skipped because its image is built locally.

Both accept `--dry-run` and print the argv they would use.

## `config`

```sh
container-compose config
container-compose config --json
```

Prints the resolved stack — defaults filled in, substitutions resolved, host
paths absolute, dependency order resolved — without contacting the runtime. Two
useful properties fall out: `config` works with no `container` installed, and
`config --json` is the document tests and diffs compare. Env values are redacted
in both forms; the `config_hash` printed beside them is computed over the
unredacted model, so a changed secret still changes the hash.

## Exit codes

| code | meaning |
|---|---|
| 0 | success, including a no-op `down`. |
| 1 | a runtime command failed, or the stack failed after it started changing things. |
| 2 | usage error or invalid stack file. Nothing was executed. |
| 3 | refused: an unowned name, a detached stack that asks for restarts, a config drift with `--no-recreate`, a volume that would have to be recreated. Nothing was executed. |
| 4 | readiness timeout: containers are running but did not become healthy. |
| 5 | the runtime is unavailable: `container` not found, `container system status` failing, or a version whose output the tool cannot parse. |
| 130 | interrupted by a second SIGINT. |

Exit 3 and exit 5 are separated because they have different fixes: 3 is the
stack or the machine's existing state, 5 is the runtime installation.

## Signals and streams

- **stdout** carries the result — a plan, a table, a JSON document. **stderr**
  carries progress and diagnostics. `--json` writes exactly one JSON document to
  stdout and nothing else.
- `SIGINT` (first): stop the supervisor, stop services in reverse order, exit 0.
- `SIGINT` (second): `container kill`, exit 130.
- `SIGTERM`: the same as the first SIGINT, without the chance to press it twice.
- While `up` is in its start phase, a signal stops the services it started in
  this invocation, matching the failure path in
  [`01-model.md`](01-model.md#partial-failure).
- Child `container` processes are never left orphaned: the tool waits for the
  child it signalled, and a `container` call has its own timeout only for
  healthchecks (`healthcheck.timeout`), not for create/start.

## What the CLI will not do

- **No `--all`, no `prune`, no `rm -f` on a name it does not own.** The tool
  touches only labelled resources, and a forced delete of an unknown name is
  never issued.
- **No shell.** Every argv is a vector; no command string is assembled and
  passed to `sh -c`.
- **No implicit file.** No `compose.yml`, no `.container-compose.toml`, no
  upward search. One path, named or defaulted, and an error when it is missing.
- **No background daemon.** `up` without `-d` owns the terminal until it exits.
